# Теория. Как проектировать тесты для существующей программы

## С чего начинается работа

При тестировании существующей системы у вас есть две разные вещи: описание того, что система **должна** делать, и код, который показывает, что она **делает сейчас**. Ожидаемый результат теста получают из согласованных требований. Код нужен, чтобы узнать интерфейс программы, запустить проверку и увидеть фактический результат.

В Gilded Rose требование «качество зачарованного товара снижается вдвое быстрее» сообщает правило поведения. Метод `update_quality()` сообщает, где наблюдать результат. Если взять ожидаемое значение прямо из метода, тест подтвердит текущую реализацию даже тогда, когда она расходится с требованием.

Для этой КТ используйте зафиксированные правила. (Они есть в файле с заданием) Они дополняют исходное описание точными числами и порядком расчёта. Прочитать [исходный текст требований](https://github.com/emilybache/GildedRose-Refactoring-Kata/blob/d6407909c73b2ba61bfa7568af0d9bdce1902fd5/GildedRoseRequirements_ru.md) полезно, чтобы увидеть, какие уточнения потребовались для проверяемой спецификации.

## Как уточнять требования к действующей системе

Сначала опишите внешнее поведение, которое можно проверить. Для Gilded Rose входом служат имя товара, `sell_in` и `quality` до обновления. Действием служит один вызов метода. Выходом служат значения двух полей после вызова. Внутренние ветки метода в требование включать не нужно: одну и ту же задачу программа может реализовать разными способами.

Затем разделите сведения по происхождению. Письменное правило выражает намерение. Наблюдение за программой показывает текущее поведение. Предположение заполняет пробел, пока владелец требований не даст ответ. При противоречии не превращайте наблюдение или предположение в правило без явного решения.

В исходном описании Gilded Rose есть примеры вопросов, которые мешают рассчитать точный результат:

| Фраза в описании | Чего не хватает для теста | Уточнение, принятое для КТ1 |
| --- | --- | --- |
| Обычный товар теряет качество, после срока — вдвое быстрее | На сколько единиц он теряет качество до срока | 1 до срока, 2 после |
| `Aged Brie` увеличивает качество с возрастом | На сколько единиц за обновление | 1 до срока, 2 после |
| Качество пропуска падает до 0 после концерта | Как трактовать `sell_in=0` при одном обновлении | Исходное `sell_in=0` относится к состоянию после концерта |
| `Conjured` теряет качество вдвое быстрее | Как тест распознаёт товар этой категории | `Conjured Mana Cake` закреплён как зачарованный товар |

Такие ответы нужно фиксировать рядом с заданием в версионируемом документе. Тогда студент, преподаватель и автоматический тест рассчитывают одно и то же ожидание. В этой работе таким документом служит `requirements.md`. Если в реальном проекте ответ ещё не получен, запишите вопрос и не называйте разницу с программой подтверждённым дефектом.

## От описания к проверяемому

Для каждого правила определите четыре части.

1. **Условие.** К какому товару и к какому исходному состоянию правило относится.
2. **Действие.** В этой работе это один вызов `update_quality()`.
3. **Наблюдаемый результат.** Новые значения `sell_in` и `quality`.
4. **Источник ожидания.** Пункт `requirements.md`, из которого рассчитаны значения.

Например, у обычного товара с `sell_in=3` и `quality=10` срок до вызова ещё не истёк. После одного обновления ожидаются `sell_in=2` и `quality=9`. Для обычного товара с `sell_in=0` действует уже другое правило. Ожидание записывают **до запуска** теста.

Если описание не позволяет вычислить результат однозначно, это пробел в требованиях. Его нужно сформулировать как вопрос. В реальном проекте ответ подтверждают с заказчиком или владельцем продукта и только после этого закрепляют в спецификации. В этой КТ ответы на такие вопросы уже внесены в `requirements.md`.

## Как выбрать небольшое число сильных проверок

**Класс эквивалентности** объединяет состояния, к которым применяется одно правило. Для обычного товара это, например, состояние до срока и состояние после его истечения. Для пропуска на концерт классов больше из-за интервалов `sell_in`.

**Граница** проходит там, где меняется правило. Соседние значения помогают заметить ошибку ровно на переходе. В Gilded Rose полезны пары `1/0` для истечения срока, `11/10` и `6/5` для пропусков. В паре `11/10` оба значения нужно подать как исходное `sell_in` в разных тестах.

**Предел** проверяет, что качество не выйдет из допустимого диапазона. Например, при исходном `quality=0` обычный товар не должен получить отрицательное качество. Предел качества 50 проверяют у товаров, качество которых растёт.

Набор из нескольких средних значений одного класса даёт меньше информации, чем проверки разных типов, границ и пределов. Перед автоматизацией составьте таблицу случаев. Так видно, какие правила уже покрыты и какие ещё остались без проверки.

## Как рассчитать оракул и сохранить связь с правилом

**Оракул теста** — обоснование ожидаемого результата. Для одного случая запишите исходный товар, применённое правило, арифметику одного обновления и ожидаемую пару полей. Ссылка на правило позволяет проверить расчёт отдельно от кода.

Удобная цепочка выглядит так:

`правило → случай в таблице → автоматизированный тест → результат прогона`

Дайте случаям номера `T01`, `T02` и так далее. Тот же номер можно использовать как идентификатор параметра Pytest. Тогда падение сразу связывается со строкой таблицы. Проверяйте оба поля, поскольку они участвуют в результате одного обновления.

## Как разбирать падение

Падение теста показывает различие между ожидаемым и фактическим результатами. Проверьте последовательно:

1. Правильно ли выбраны имя товара и исходные данные.
2. Верно ли определён класс и исходное значение `sell_in`.
3. Правильно ли рассчитаны оба ожидаемых поля по `requirements.md`.
4. Повторяется ли фактический результат при запуске только вашего файла.

Если ошибочен расчёт, исправьте тест и объясните причину. Если правило оставляет несколько возможных результатов, запишите вопрос по требованию. Если входные данные и ожидание верны, оформите дефект с шагами, ссылкой на правило, ожидаемым и фактическим результатом. Не меняйте ожидание только ради зелёного прогона.
