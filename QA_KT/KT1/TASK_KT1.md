# КТ1. От требований к тестам на примере Gilded Rose

## Цель

Спроектировать проверки для существующей программы по письменным правилам, выбрать данные для разных классов и границ, связать каждое ожидание с правилом, реализовать часть случаев на Pytest и объяснить результаты запуска.

Перед работой прочитайте [теорию о проектировании тестов для существующего проекта](theory.md) и [правила Gilded Rose для КТ1](requirements.md). Последний документ служит источником ожидаемых результатов. Исходный код служит источником фактических результатов.

## Исходные материалы

Работайте в каталоге `python` учебного репозитория. Программа находится в `python/gilded_rose.py`. Класс `Item(name, sell_in, quality)` описывает товар, а `GildedRose(items).update_quality()` обновляет товары за один день. За основу взят [GildedRose-Refactoring-Kata, коммит `d6407909c73b2ba61bfa7568af0d9bdce1902fd5`](https://github.com/emilybache/GildedRose-Refactoring-Kata/tree/d6407909c73b2ba61bfa7568af0d9bdce1902fd5). В учебном репозитории должны находиться код этой версии и три файла задания: `KT1.md`, `theory.md`, `requirements.md`.

Для проверки достаточно Python 3.10+ и Pytest 9.1.1. В PowerShell из каталога `python` создайте окружение и установите Pytest:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install pytest==9.1.1
```

Если команда `py` недоступна, используйте установленный `python` версии 3.10 или новее. Если в вашем экземпляре учебного репозитория нет каталога `python`, сообщите преподавателю: для этой КТ он является обязательным исходным материалом.

## Модель одного обновления

Товар задаётся как `Item(name, sell_in, quality)`. Один вызов `GildedRose([item]).update_quality()` соответствует одному дню. `sell_in` и `quality` после вызова сравниваются с состоянием до вызова.

Для выбора правила используйте **исходное** значение `sell_in`. Если оно больше 0, срок ещё не истёк. Если оно равно 0 или меньше, срок истёк. Значение `sell_in` уменьшается на 1 при каждом обновлении, кроме товара `Sulfuras`. Это правило действует даже тогда, когда качество уже достигло предела.

Для этой работы используйте целочисленные `sell_in` и `quality`. Начальное качество всех товаров, кроме `Sulfuras`, находится в диапазоне от 0 до 50. После обновления их качество также остаётся в этом диапазоне. У `Sulfuras` качество равно 80.

## Правила по типам товаров

| Тип | Точное имя для тестов | Изменение качества за одно обновление |
| --- | --- | --- |
| Обычный товар | Любое имя, отличное от трёх особых имён ниже и `Conjured Mana Cake` | При исходном `sell_in > 0` качество уменьшается на 1, при `sell_in <= 0` — на 2. Нижний предел 0. |
| Выдержанный сыр | `Aged Brie` | При исходном `sell_in > 0` качество увеличивается на 1, при `sell_in <= 0` — на 2. Верхний предел 50. |
| Пропуск на концерт | `Backstage passes to a TAFKAL80ETC concert` | При исходном `sell_in > 10` качество увеличивается на 1, при `6 <= sell_in <= 10` — на 2, при `1 <= sell_in <= 5` — на 3. При `sell_in <= 0` качество становится 0. Верхний предел 50. |
| Легендарный товар | `Sulfuras, Hand of Ragnaros` | `sell_in` не меняется, `quality` остаётся 80. |
| Зачарованный товар | `Conjured Mana Cake` | При исходном `sell_in > 0` качество уменьшается на 2, при `sell_in <= 0` — на 4. Нижний предел 0. |

Для `Conjured` применяется правило «вдвое быстрее обычного товара» из исходных требований. Точное имя закреплено здесь, чтобы тест и программа получали одни и те же входные данные. В этой КТ не требуется задавать правило для других названий зачарованных товаров.

## Приоритет правил

Сначала определите тип товара по имени. Затем по исходному `sell_in` выберите изменение качества. Примените предел качества, если он нужен. После этого определите новое `sell_in`. Такой порядок нужен для расчёта ожидания и не предписывает внутреннее устройство программы.

Исходный код показывает фактический результат. Ожидаемый результат теста рассчитывайте по этим правилам. Если программа ведёт себя иначе, сохраните правило и зафиксируйте расхождение.

## Задание

1. Составьте в `python/test_cases.md` таблицу не менее чем из **8 тестовых случаев**. Покройте обычный товар до и после срока, качество на нижнем пределе 0, `Aged Brie`, `Backstage passes`, `Sulfuras` и `Conjured Mana Cake`. Включите **две пары соседних значений по разные стороны границы**: `sell_in=1/0` для обычного товара и одну пару для пропуска на концерт — `11/10` либо `6/5`. Для каждого случая запишите пункт правила, входной `Item`, действие, ожидаемые `sell_in` и `quality`, причину выбора данных.
2. Выберите из таблицы минимум **4 случая** и реализуйте их в `python/tests/test_student_design.py`. Среди них должна быть хотя бы одна пара соседних значений границы и один случай для `Conjured Mana Cake`. Ожидаемые значения запишите самостоятельно до запуска. Сравнивайте оба поля товара.
3. Из каталога `python` запустите **только свой файл**:

   ```powershell
   .\.venv\Scripts\python.exe -m pytest -q tests/test_student_design.py
   ```

4. Для каждого падения проверьте входные данные, правило и расчёт ожидания. В `python/run.txt` запишите команду, версии Python и Pytest, краткое резюме прогона и причину каждого падения. В `python/defect.md` оформите хотя бы одно подтверждённое расхождение с правилом. Если подтверждённых расхождений нет, объясните, что было проверено и какие области остались без проверки.
5. Сдайте четыре файла: `python/test_cases.md`, `python/tests/test_student_design.py`, `python/run.txt`, `python/defect.md`. Код `python/gilded_rose.py` в этой работе не меняйте.

Если в учебном репозитории сохранён исходный `python/tests/test_gilded_rose.py`, его учебный `test_foo` намеренно падает на ожидании `fixme`. Не запускайте его в составе своего прогона и не включайте это падение в отчёт о найденном дефекте.
