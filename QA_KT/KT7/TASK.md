# КТ7. Релизный аудит IncidentDesk

## Ситуация

К выпуску готовиться сервис для регистрации внутренних инцидентов. Разработчики говорят что все ок, все тесты зеленые. Ваша задача, как инженера, определить, какие требования и границы доступа действительно проверены, после подправить и усилить тесты, и передать решение о выпуске, выпускаем мы этот продукт, или нет. Решение нужно обосновать.

В проекте есть библиотека `src/IncidentDesk` и начальный набор проверок `tests/IncidentDesk.Tests/ExistingTests.cs`. У вас есть исходный код, поэтому его можно читать. Выводы о поведении продукта подтверждайте исполняемыми тестами.

## Контракт продукта

Пользователи принадлежат командам. Возможные роли: `Reporter` (автор заявки), `Responder` (исполнитель), `Coordinator` (координатор), `Auditor` (аудитор). Инцидент проходит состояния `New → InProgress → Closed`.

- `Reporter` создаёт инциденты в своей команде, получает и видит в списке **только собственные** инциденты, меняет название собственного инцидента только в состоянии `New`.
- `Responder` читает инциденты своей команды и начинает работу только над назначенным ему инцидентом в состоянии `New`.
- `Coordinator` читает инциденты своей команды, назначает на новые инциденты исполнителя из той же команды и закрывает инцидент своей команды только после начала работы.
- `Auditor` читает инциденты всех команд, но не меняет их.
- Любое действие, на которое у роли нет права, вызывает `AccessDeniedException`. Действие, которое разрешено роли, но невозможно в текущем состоянии инцидента, вызывает `InvalidIncidentStateException`. Запрещённое действие не должно менять сохранённый инцидент.

### Проверяемые требования и вес риска

Вес 1–5 отражает ущерб от пропуска проверки: 5 — возможная утечка данных или изменение без права, 1 — небольшой локальный сбой. Пункты специально разделены на наблюдаемые условия. Покрытым считается пункт, для которого тест **прямо проверяет ожидаемый результат утверждением**, а не просто вызывает метод.

| ID | Ожидаемое поведение | Вес |
| --- | --- | ---: |
| T01 | `Reporter` создаёт инцидент своей команды в состоянии `New`. | 2 |
| T02 | Пустое или состоящее из пробелов название отклоняется. | 1 |
| T03 | `Reporter` получает собственный инцидент через `Get`. | 2 |
| T04 | `Reporter` не получает через `Get` инцидент другого автора той же команды. | 5 |
| T05 | `List(Reporter)` содержит собственный инцидент. | 2 |
| T06 | `List(Reporter)` не содержит инцидент другого автора той же команды. | 5 |
| T07 | `Responder` не получает через `Get` инцидент чужой команды. | 4 |
| T08 | `Coordinator` не получает через `Get` инцидент чужой команды. | 4 |
| T09 | `Auditor` получает через `Get` инцидент чужой команды. | 2 |
| T10 | `Reporter` переименовывает собственный инцидент в состоянии `New`. | 2 |
| T11 | `Reporter` не переименовывает собственный инцидент в состоянии `InProgress`. | 3 |
| T12 | `Coordinator` назначает исполнителя своей команды на новый инцидент. | 2 |
| T13 | `Coordinator` не назначает исполнителя чужой команды. | 4 |
| T14 | Назначенный `Responder` переводит новый инцидент в `InProgress`. | 2 |
| T15 | Другой `Responder` не начинает работу над не назначенным ему инцидентом. | 4 |
| T16 | `Coordinator` своей команды закрывает инцидент в `InProgress`. | 2 |
| T17 | `Coordinator` чужой команды не закрывает инцидент. | 4 |
| T18 | `Auditor` не закрывает инцидент. | 5 |

## Ваша задача

1. Запустите исходные тесты. Запишите результат прогона. Составьте матрицу «требование - имеющийся тест - статус» для всех T01–T18. Не засчитывайте проверку, которая подтверждает только противоположную, разрешённую сторону правила.
2. Посчитайте начальное **покрытие требований**: число требований с прямой проверкой / 18. Посчитайте **покрытие с учётом риска**: сумма весов требований с прямой проверкой / сумма всех весов. Укажите, какие права и переходы остаются непроверенными.
3. У вас лимит на **четыре новых тестовых сценария**. Один должен проверить видимость списка для двух авторов одной команды; один -- запрет изменения инцидента пользователем без права; один -- правило перехода состояния; четвёртый выберите сами по максимальному оставшемуся риску. Каждый сценарий должен закрывать хотя бы один пробел исходного набора. Используйте минимум две роли и две команды в новых данных. Один сценарий — одна независимая подготовка данных и проверка поведения; одна строка `[Theory]` считается отдельным сценарием. Можно писать несколько утверждений об одном результате.
4. Добавьте тесты в новый файл проекта `tests/IncidentDesk.Tests`. Не меняйте исходный набор тестов и библиотеку. Для запретов проверяйте тип исключения; хотя бы в одном тесте дополнительно проверьте, что инцидент после отказа не изменился.
5. Запустите весь набор и соберите покрытие кода **до и после** добавления тестов. В `coverage.cobertura.xml` найдите `line-rate` и `branch-rate` (доли от 0 до 1). Сравните эти числа с покрытием требований. Увеличение процента строк само по себе не доказывает соблюдение прав.
6. Заполните `REPORT_TEMPLATE.md`: матрица до/после, результаты четырёх тестов, расчёты, найденный дефект (если есть), оставшийся риск и решение «выпускать / задержать» с объяснением. Если тест с корректным ожиданием падает, это полезная находка; не меняйте ожидание только ради зелёного прогона.

## Как запустить

Нужны .NET SDK 10 и доступ к NuGet при первом восстановлении пакетов. Откройте терминал в папке с `IncidentDesk.sln`:

```powershell
dotnet test IncidentDesk.sln
dotnet test IncidentDesk.sln --collect:"XPlat Code Coverage"
```

Команда покрытия выводит путь к файлу `coverage.cobertura.xml` в `tests/IncidentDesk.Tests/TestResults/<номер-прогона>/`. Первый отчёт сохраните отдельно до написания тестов, затем сравните его со вторым. Атрибуты `line-rate` и `branch-rate` в корневом элементе XML умножьте на 100 для процентов.

## Что сдавать

- Ваш `.cs`-файл с четырьмя новыми сценариями.
- Заполненный `REPORT_TEMPLATE.md`.
- Вывод двух прогонов и два файла `coverage.cobertura.xml` или снимки их корневых строк с датой/именем прогона. Если итоговый прогон красный из-за найденного дефекта, приложите его вывод.
