# Как исследовать неисправную программу

## 1. Что известно до исследования

У вас есть программа и требования R1–R6. Правила описывают, как она должна работать. Код показывает, как она работает сейчас, и может содержать ошибки. Исправлять ожидания под текущий код нельзя.

Готовый тест выдачи одного микрофона проходит. Он подтверждает конкретный пример. Другие входы и последовательности требуют собственных проверок. Число и места неисправностей в студенческих материалах не раскрываются.

Преподаватель показывает запуск и синтаксис проходящего теста. Вы самостоятельно выбираете направления поиска, данные и порядок действий.

## 2. Составить короткий план

Перед изменением кода запишите: что проверяете, по какому правилу, на каких данных и чего ожидаете. Выберите порядок по последствиям возможной ошибки. Если неверное поведение может исказить учёт, объясните, почему его исследование важно.

В плане также нужны условия начала и завершения. Например, начинать осмысленный поиск можно после запуска программы на известных исходных данных. При расхождении нужно остановить текущую правку и разобраться в наблюдении. Завершать следует после проверки исправлений и соседних случаев. Если времени не хватило, запишите невыполненное и оставшиеся сомнения.

Это рабочие решения для вашего исследования, а не отдельный большой документ. После нового наблюдения план можно дополнить. Исходное ожидание сохраняют, если оно подтверждено требованием.

## 3. Как выбирать данные

Используйте изученные техники самостоятельно:

- **Классы эквивалентности:** выделить группы входов, для которых действует одно правило; выбрать представителей разных групп.
- **Границы:** найти места, где по требованию меняется допустимость или результат; проверить значения около перехода и на нём.
- **Сочетания условий:** различать несколько причин отказа и учитывать установленный порядок их проверки.
- **Состояния и последовательности:** учесть историю действий, если одинаковая операция в разных состояниях должна дать разные результаты.

Случайный ввод не заменяет осмысленного выбора. В протоколе должно быть понятно, какое правило проверяет каждый выбранный случай. Конкретные данные для обнаружения ошибок вы подбираете сами.

## 4. Сделать проверку исполнимой

В проекте есть проходящий пример:

```python
import unittest
from mediapolka import issue, new_state

class StartTests(unittest.TestCase):
    def test_issue_one_microphone(self):
        state = new_state()                  # подготовка
        result = issue(state, "mic", "1")     # действие
        self.assertTrue(result["ok"])
        self.assertEqual(state["stock"]["mic"], 2)
        self.assertEqual(len(state["loans"]), 1)
```

`assertEqual(факт, ожидание)` сравнивает значения. В этом примере ожидание 2 вычислено заранее: в начале 3, выдали 1. Тест не спрашивает у программы, какое значение считать правильным.

Ваши методы добавляются в `tests/test_student.py`. Имя метода начинается с `test_`, имя файла — с `test_`. Каждый тест должен иметь самостоятельную цель. Несколько копий одного теста с новым именем не расширяют исследование.

Запуск из папки `project`: `py -3 -m unittest discover -s tests -v`. Модуль `unittest` встроен в Python. Он позволяет выражать те же проверки входов и ожиданий, для которых в других работах курса использовался Pytest.

## 5. Отличить неисправность программы от проблемы проверки

При падении найдите имя теста, неуспешное утверждение, ожидаемое и фактическое значение. Сверьте исходное состояние, правило и свой расчёт. Только после этого решайте, ошибочна программа или сама проверка.

Ошибка импорта, синтаксиса или запуск нулевого числа тестов ещё не подтверждают неисправность продукта. Сначала восстановите корректное выполнение теста. Для просмотра промежуточных значений можно временно использовать `print` или знакомый отладчик редактора.

Чтобы проверить отсутствие изменений, сравнивайте состояние со снимком `deepcopy`, сделанным до действия. Простое присваивание второй переменной не создаёт независимую копию изменяемого словаря.

## 6. Порядок починки

1. Воспроизвести расхождение на известных данных.
2. Сверить ожидание с конкретным правилом.
3. Написать тест и убедиться, что он падает по причине этого расхождения.
4. Сохранить вывод запуска до изменения кода.
5. Найти причину и исправить логику.
6. Запустить тот же тест и весь набор, затем добавить соседнюю проверку.

Не удаляйте неуспешный тест, не пропускайте его и не заменяйте ожидание результатом неисправной программы. Исправление должно восстанавливать правило, а не только узнавать один тестовый вход.

## 7. Независимость и история

Каждый независимый тест начинает со своего `new_state()`. Иначе следующий тест может получить данные, оставшиеся после предыдущего, и падение будет трудно объяснить.

Внутри одного сценария сохраняйте состояние между действиями: иначе вы не проверите историю. Где нужен отдельный вход, а где последовательность, определяйте из требований. Если состояние меняется, одного сообщения об успехе недостаточно: важно проверить сами данные.

## 8. Доказательство результата

Для каждой причины сохраните правило, входы/шаги, ожидание, факт до исправления, имя обнаруживающего теста, изменение кода и повторный результат. Разные проявления одной и той же причины не следует выдавать за независимые неисправности.

Зелёный итоговый запуск подтверждает выбранные случаи. В конце назовите непроверенные места и ограничьте вывод тем, что действительно проверяли.

На экзамене будут новый экземпляр и требования, редактор и запуск тестов. Готового каркаса тестов и учебной памятки не будет. Поэтому уже на этом занятии все решения о поиске и исправлении вы принимаете самостоятельно.
