# 2. Классификация и выбор методов и техник проектирования тестов

## Выбор техники начинается с правила

Для диапазона значений подходят классы эквивалентности и граничные значения. Для сочетания условий — таблица решений. Для поведения, которое зависит от предыдущих действий, — модель состояний (тема 3). Техника помогает выбрать небольшой набор информативных случаев; она не заменяет чтение требований.

## Классы эквивалентности

Разделите входы на группы, внутри которых действует одно правило. Для обычного товара в Gilded Rose важны, например, срок **до истечения** и **после истечения**. Один представитель каждого класса даёт начальную проверку, но на переходе между классами нужны отдельные граничные случаи.

Не соединяйте значения в один класс только потому, что тип данных одинаковый. `sell_in=5` и `sell_in=0` — целые числа, но правила изменения качества различаются. Не считайте классы полными, пока не рассмотрены специальные типы товаров и пределы качества.

## Граничные значения

Для порога `x` обычно проверяют значение до него, само значение и значение после него. Если поведение пропуска меняется при `sell_in ≤ 10`, полезны `11`, `10` и `9`; у следующего порога — `6`, `5` и `4`. Для истечения срока проверьте, что именно считается «после» одного обновления: исходное `sell_in=0` превращается в `-1`.

Отдельно проверьте пределы результата. Если качество ограничено интервалом `0…50`, тесты возле `0` и `50` должны проверять и новое значение качества, и изменение срока. У исключения вроде `Sulfuras` правило может отличаться от общего ограничения — это нужно явно зафиксировать, а не применять общий тест ко всем товарам.

## Таблица решений

Когда результат зависит от нескольких условий, выпишите условия и действия. Упрощённый пример для обычного товара:

| Срок истёк после обновления? | Качество до обновления больше 0? | Ожидаемое действие |
| --- | --- | --- |
| Нет | Да | Уменьшить качество по обычному правилу |
| Да | Да | Уменьшить качество быстрее |
| Любое | Нет | Не уходить ниже нуля |

Эта таблица — модель для выбора случаев, а не дословная реализация кода. При добавлении типа товара появляются новые строки или отдельная таблица. Если таблица слишком велика, сначала покрывайте критичные комбинации и границы, затем объясните, какие сочетания оставлены вне набора.

## Практический порядок

1. Запишите правило своими словами и укажите его источник.
2. Выберите технику по форме правила: диапазон, сочетание условий или последовательность действий.
3. Выпишите классы или условия и рядом — границы.
4. Для каждого случая рассчитайте ожидаемый результат **до запуска программы**.
5. После запуска отметьте покрытые правила и обоснованные пробелы.

## Самопроверка

1. Почему один случай с `sell_in=5` не проверяет истечение срока?
2. Какие значения нужны по обе стороны порога `10`?
3. Когда таблица решений полезнее простого списка входных значений?

Применение: используйте классы и границы в [ПР 1](../practice/01_requirements_and_tests.md); в ПР 2 они будут реализованы параметризованными тестами.
