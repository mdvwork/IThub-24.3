# 1. Основные понятия и принципы проектирования тестов

## Что проектирует тестировщик

Тестирование начинается с вопроса **какое поведение требуется**, а не с запуска программы. Требование задаёт правило, тестовый случай — конкретное начальное состояние, действие и ожидаемый результат. Выполнение теста добавляет фактический результат. Разница между ожидаемым и фактическим требует анализа: причиной может быть дефект программы, неверный тест или неполное требование.

| Понятие | Практический смысл |
| --- | --- |
| Объект тестирования | Функция, компонент, API или пользовательский сценарий, поведение которого проверяется. |
| Условие тестирования | Правило или риск, ради которого нужна проверка. |
| Тестовый случай | Входные данные, исходное состояние, действие и ожидаемый результат. |
| Оракул теста | Основание, по которому рассчитано ожидание: требование, спецификация, договорённость или проверенная модель. |
| Набор тестов | Случаи, выбранные для общей цели: регрессии, проверки функции, релиза. |
| Результат выполнения | Фактические данные, версия кода, команда запуска и вывод о совпадении с ожиданием. |

Например, правило «качество обычного товара уменьшается на 1 за день до истечения срока» можно проверить на начальном состоянии `sell_in=5`, `quality=10`. После одного обновления ожидаются `4` и `9`. Числа в ожидании выводятся из правила, а не копируются из результата программы.

## Трассировка и достаточность

Полезная короткая цепочка: **требование → тестовый случай → исполнимый тест → результат → вывод**. Она показывает, зачем существует тест, и помогает заметить правило без проверки. Один тест может покрывать несколько правил, но тогда труднее понять причину падения. При учебной работе лучше предпочитать ясные проверки с понятным оракулом.

Много тестов не означает хорошее покрытие. Если все проверки используют обычные значения, они могут пропустить переходы: истечение срока, достижение максимума, смену состояния задачи. Приоритет определяют риск ошибки, важность поведения и стоимость проверки. Проверяйте ограничения, исключения и сочетания условий там, где ошибка даст заметный эффект.

## Что означает зелёный и красный тест

Зелёный тест подтверждает совпадение **одного проверенного примера** с ожиданием. Он не доказывает, что функция верна на всех входах. Красный тест полезен, если ожидание подтверждено и вход можно воспроизвести. Перед отчётом о дефекте нужно проверить версию кода, входные данные и собственный расчёт. Не меняйте ожидаемое число только ради зелёного результата.

При использовании AI запрашивайте варианты тестовых данных и пропущенные риски, затем сами сверяйте каждое ожидаемое значение с требованием. На защите нужно уметь объяснить тест без текста, сгенерированного инструментом.

## Самопроверка

1. Какая часть тестового случая отвечает на вопрос «почему результат должен быть именно таким»?
2. Может ли прошедший тест доказать отсутствие дефектов во всём приложении? Почему?
3. Что нужно проверить перед тем, как назвать падение теста дефектом программы?
