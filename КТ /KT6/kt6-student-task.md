Черновик описывает **действующий** сервис, но не считается безошибочным. Для проверки используйте собственные задачи с узнаваемым названием. Номера задач берите из ответов на `POST`: они отличаются между запусками. Исходный код, Python и Selenium для работы не нужны.

# Черновик описания Todo API для ревью в КТ6

Сервис хранит задачи с полями `id`, `name` и `isComplete`. Оператор иногда создаёт две задачи с одинаковым названием для разных случаев; различать их он должен по `id`. Другой сценарий — изменить только признак выполнения задачи, сохранив её название.

## Операции

| Запрос | Описание | Ответ |
|---|---|---|
| `POST /todoitems` | Создаёт задачу из `name` и `isComplete`. Если задача с таким `name` уже есть, повторное создание отклоняется. | При создании — `201 Created`, объект с новым `id` и заголовок `Location`. При совпадении `name` — `409 Conflict`. |
| `GET /todoitems` | Возвращает все задачи. | `200 OK`, массив задач. |
| `GET /todoitems/complete` | Возвращает только задачи с `isComplete: true`. | `200 OK`, массив задач. |
| `GET /todoitems/{id}` | Возвращает задачу по её `id`. | Для существующей задачи — `200 OK` и объект; для отсутствующей — `404 Not Found` без тела. |
| `PATCH /todoitems/{id}` | Изменяет только поля, переданные в JSON. Если передан один `isComplete`, `name` остаётся прежним. | Для существующей задачи — `204 No Content` без тела. |
| `PUT /todoitems/{id}` | Для смены только статуса достаточно передать `isComplete`; пропущенное поле `name` сохранит прежнее значение. | Для существующей задачи — `204 No Content` без тела. |
| `DELETE /todoitems/{id}` | Удаляет задачу. Повторный `DELETE` с тем же `id` также возвращает `204`, потому что удаление идемпотентно. | `204 No Content` без тела при первом и повторном запросе. |

## Задача

Проведите небольшое ревью черновика по критериям **полнота, однозначность, непротиворечивость, проверяемость**. Найдите **три разных существенных замечания**. В этом варианте: требуется проследить состояние задач до и после действий и отличить ошибочное утверждение от того, что проверка пока не доказывает.

### 1. До отправки запросов

Составьте короткий чек-лист из **четырёх проверок** по черновику. Для каждой запишите:

- какую фразу проверяете;
- какие данные нужны в начале;
- какой статус и/или изменение полей ожидаются **по тексту черновика**;
- каким запросом прочитаете итоговое состояние.

Три проверки должны быть направлены на спорные утверждения, одна — на утверждение, которое может оказаться верным. Этот шаг нужен, чтобы не подгонять ожидаемый результат под уже увиденный ответ.

### 2. Проверьте сервис в Scalar

Постройте **свою минимальную** последовательность запросов так, чтобы в ней были:

1. **Как минимум две новые задачи с заранее выбранным исходным состоянием.** Подберите значения так, чтобы проверить спорную фразу о создании, и запишите оба `id` из ответов `POST`.
2. **Сравнение `PATCH` и `PUT` на сопоставимых исходных данных.** Сами выберите тело обновления; для честного сравнения сохраняйте одинаковыми начальное состояние и набор переданных полей. После каждого обновления прочитайте задачу через `GET /todoitems/{id}` и сравните оба поля с исходными значениями. Одного ответа `204 No Content` для вывода недостаточно.
3. **Проверка утверждения об удалении на протяжении жизненного цикла одной записи.** Зафиксируйте ответы при первом и последующем действии с тем же `id`, а также состояние записи после них.
4. **Одна контрольная проверка корректного утверждения черновика.** Запишите, почему его не следует включать в список замечаний.

Продумайте порядок действий: если удалить задачу слишком рано, она уже не подойдёт для сравнения обновлений. Все запросы выполняйте через Scalar; программировать и менять сервер не требуется.

### 3. Разберите результаты

Для каждого из трёх замечаний укажите точную цитату, нарушенный критерий, ожидаемый по черновику результат, фактический ответ и **состояние задачи после запроса**. Предложите короткую замену текста, по которой другой человек сможет повторить проверку. Не разбивайте одно расхождение на два замечания только потому, что вы отправили два запроса.

Если работающий API противоречит фразе о желаемом сценарии клиента, не объявляйте автоматически виноватым только код или только документ. Укажите, как сейчас следует пользоваться API, и сформулируйте вопрос владельцу требований о желаемом поведении.

**Отдельный вопрос:** в конце черновика есть предложение редактора о сортировке. Можно ли превратить его в гарантию API на основании одного увиденного списка? Запишите решение и один вопрос, который нужно задать перед публикацией такой гарантии.

## Что сдать

Один Markdown-файл объёмом примерно **1–2 страницы**:

1. Чек-лист из четырёх строк с ожиданиями, записанными до проверки.
2. Краткий журнал запросов: метод, адрес, существенные поля тела, статус, значимые поля ответа и `id`. Скриншоты Scalar допустимы, но необязательны, если можете показать журнал.
3. Таблицу из **трёх** замечаний:

   | Цитата и критерий | Ожидание по черновику | Факт и проверка состояния | Точная правка или вопрос |
   |---|---|---|---|

4. Одно подтверждённое корректное утверждение, вывод о сортировке и **одно предложение** о самом опасном замечании и причине выбора.
